# CF-Chef Oven Controller — Design Specification

Source: `OSHP_files/Clean/CF-Chef` (vendored submodule of https://github.com/reilleya/CF-Chef).
Repo one-line description (`readme.md`): "This repository contains the KiCAD PCB design and rust firmware for an oven controller intended for use in custom composite curing ovens."

This document is grounded strictly in the schematic/netlist (`controller.kicad_sch`, `power.kicad_sch`, `thermocouples.kicad_sch`, `mcu.kicad_sch`, `controller.net`), the vendored component libraries under `hardware/controller/components/`, the Rust firmware under `firmware/src/`, and the project's own commit history. Where the repository shows *what* was built but not *why*, that is marked **Inferred**.

## 1. TL;DR

The board is a single ESP32-C3 based controller (`U1`, ESP32-C3-MINI-1) for a resistive-heating composite-curing oven. It:

- Reads up to **3 K-type thermocouples** (`U2`, `U3`, `U4` — MAX31855KASA, one per `thermocouples.kicad_sch` zone) over a shared SPI bus (SCK/SO + 3 independent chip-selects CS0–CS2), confirmed by `firmware/src/bin/main.rs` (`NUM_THERMOCOUPLES = 3`, SPI2 on GPIO5/GPIO10, CS pins GPIO4/6/7).
- Drives a single **heater output** net through a smart high-side switch (`U6`, TPS1H200AQDGNRQ1) switched from the ESP32's GPIO1, using simple bang-bang control (firmware: `if average_temp < config.temperature { heater_output.set_high() } else { heater_output.set_low() }`).
- Monitors **2 fan tachometers** (`NUM_FANS = 2`) with TVS-diode-protected inputs, and raises a run fault if a fan stalls.
- Accepts power from either a **12 V barrel jack** (`J11`, run supply) or **USB-C 5 V** (`J12`, logic/programming supply), arbitrated by an autoswitching power mux (`U5`, TPS2121RUXR) and stepped down to 3.3 V logic by a buck converter (`U8`, AP63203WU).
- Exposes status over Wi-Fi via a small webserver (`firmware/src/web.rs`, `wifi.rs`) and a single onboard WS2812B status LED (`D1`).

The two headline protection/power decisions directly visible in the netlist are: (1) a power mux (not a diode-OR) arbitrates the two possible input supplies, and (2) the heater is switched by an automotive-grade smart high-side switch with its own hardware over-current/fault reporting, rather than a plain MOSFET — see component table below.

**Important grounding note on component selection:** the task brief for this document named four protection/power ICs as "the main why signal": MPM3606AGQV-P, TPS1H200AQDGNRQ1, LM73100RPWR, and TPS2121RUXR. Checking the actual netlist (`controller.net`) and the board's own git history shows that **only two of these four are in the shipped design**. `LM73100RPWR` and `MPM3606AGQV-P` exist solely as leftover vendored footprint/symbol libraries under `hardware/controller/components/` — they do not appear as components in `controller.net` or in the current `power.kicad_sch`/`controller.kicad_pcb`. Git history shows they were deliberately superseded:
- commit `d69e70c` *"Replace input diodes with power mux chip"* removed `LM73100RPWR` and replaced it with `TPS2121RUXR`.
- commit `fdfb582` *"Swap out voltage regulator"* removed `MPM3606AGQV-P` and replaced it with `AP63203WU`.

The component table below documents all six parts (the two actually-used ICs from the brief, the two superseded/unused ones, the buck regulator that replaced MPM3606, and the MCU) and marks each accordingly.

## 3. Power Architecture (`power.kicad_sch` / `controller.net`)

Traced net-by-net from `controller.net`:

**Inputs**
- `J11` (Barrel_Jack) → `+12V` net. Also on this net: `U5` pin 7/7_1 (`IN1`), `D7` (plain diode, `Device:D`), bulk caps `C1` (value not separately captured) and `C2`, and the two fan-header 12 V pins (`J7`/`J8` pin 2).
  - `D7`'s cathode (`K`, pin 1) is tied to `+12V` and its anode (`A`, pin 2) is tied to `GND`. In this orientation the diode is reverse-biased (non-conducting) under normal positive 12 V supply, and would only conduct if the barrel-jack supply were connected with reversed polarity or the rail were pulled negative. **Inferred:** this is a reverse-polarity/negative-transient protection diode on the 12 V input — added in commit `542887a` *"Add TVS diode to 12V rail,"* even though the part actually placed (`D7`) is a plain `Device:D`, not a `Device:D_TVS` symbol (the `D_TVS` symbols in the design, `D5`/`D6`, are used elsewhere — see Thermocouple/fan section). No in-repo comment explains the discrepancy between the commit title ("TVS diode") and the symbol actually used; this is noted as observed fact, not resolved.
  - `J12` (USB_C_Receptacle_USB2.0_14P) VBUS pins (A4/A9/B4/B9) → `+5V` net → `U5` pin 2/2_1 (`IN2`).
  - USB-C CC1/CC2 pins go through `R1`/`R7` (5.1 kΩ each) to `GND` — the standard CC pull-down value for declaring the port a default (non-PD) USB-C sink. **Inferred** as a design choice (the repo states no rationale), though 5.1 kΩ is the USB-C-spec value for this function, so the *what* (sink, default current) is a direct schematic fact, while the "no PD / no higher-current negotiation" conclusion is inferred from that standard value.

**Arbitration**
- `U5` (TPS2121RUXR) takes `IN1` = +12 V (barrel jack) and `IN2` = +5 V (USB), and outputs a single `OUT` (pins 1/1_1/8/8_1) onto the `VBUS` net (the board's internal, unregulated/pre-buck rail — note this net is named `VBUS` in the netlist but is distinct from the USB `+5V` net upstream of the mux). `PR1`(pin6)/`OV1`(pin5)/`OV2`(pin4)/`CP2`(pin3) are all tied to `GND`, i.e. left at their simplest/default configuration — no external resistor-divider overvoltage thresholds are programmed. `ILIM` (pin 10) is set by `R12` (51.1 kΩ) and `SS` (pin 11) has a 10 nF cap (`C5`); `ST`(pin9)/`GND`(pin12) go to `GND`. A 10 µF cap (`C11`) and test point (`TP1`) sit on the resulting `VBUS` net.

**Regulation**
- `VBUS` → `U8` (AP63203WU) pins `IN`(3)/`EN`(2). `U8` `SW`(5) drives the buck inductor `L1` (3.9 µH) and bootstrap cap `C13`; `FB`(1) is tied directly to `+3V3` (consistent with AP63203WU being a *fixed* 3.3 V output part, per its own symbol description, so no external feedback divider is needed); `GND`(4) → `GND`.
- Output `+3V3` net feeds: ESP32 (`U1` pin 3, `3V3`), the three MAX31855 thermocouple ICs (`U2`/`U3`/`U4` pin 4, `V_{CC}`), the WS2812B status LED (`D1` `VDD`), decoupling caps `C3/C4/C6/C8/C9/C10/C12`, and pull-up/pull-down resistors `R2/R5/R6/R11` (strapping/EN/fan-tach related — see MCU/thermocouple sections).

**Heater path**
- `+12V` also feeds `U6` (TPS1H200AQDGNRQ1) `VS` (pin 8) directly — i.e. the heating element is switched at the raw 12 V input, upstream of and independent from the regulated 3.3 V logic rail. `IN`/`DIAG_EN` (pins 1/2) are both driven from ESP32 GPIO1 (net `/Microcontroller/HEATER`), `OUT` (pin 7) feeds the heater connector `J6` pin 2, `CL` (pin 4) and `GND` (pin 6) and the exposed pad `EP` (pin 9) all go to `GND`, and `~{FAULT}` (pin 3) is broken out to test point `TP6` only (not read back by the MCU, per the firmware grep — no GPIO is wired to that signal in `main.rs`).
- A status LED (`D2`) and series resistor (`R3`) are also on the `HEATER` net, so the heater output doubles as a visual "heater on" indicator at the board level — this is a direct schematic fact, not stated as intent anywhere.

## 4. Thermocouple Sensing (`thermocouples.kicad_sch` / `controller.net`)

Three identical channels, each built around a **MAX31855KASA** (`U2`, `U3`, `U4`) — "Cold Junction K-type Thermocouple Interface, SPI, SOIC-8" per the symbol's own `Description` property, datasheet link `http://datasheets.maximintegrated.com/en/ds/MAX31855.pdf`.

Per channel (shown for `U2`, identical topology for `U3`/`U4`):
- Thermocouple wire pair connects to a 2-pin screw terminal (`J1` for `U2`, `J2` for `U3`, `J3` for `U4`) whose two pins wire directly to the MAX31855's differential thermocouple inputs `T+` (pin 3) and `T-` (pin 2).
- Power: `V_{CC}` (pin 4) → `+3V3`, `GND` (pin 1) → `GND`, with a 1 µF decoupling cap per channel (`C3` for U2, `C6` for U3, `C4` for U4 — exact mapping per schematic placement).
- SPI bus is **shared** across all three chips: `SCK` (pin 5) and `SO` (pin 7, tri-state/MISO) are common nets (`SCK`, `SO`) tied to all three ICs and to the ESP32 (`U1` GPIO5/SCK, GPIO10/SO). Each chip has its own independent chip-select: `~{CS}` (pin 6) on `U2`/`U3`/`U4` goes to separate nets `CS0`/`CS1`/`CS2`, driven by ESP32 GPIO4/GPIO6/GPIO7 respectively. There is no MOSI line wired, consistent with the MAX31855 being a read-only SPI device.
- Pin 8 (`NC`) is left unconnected on all three parts (confirmed: `unconnected-(U2/U3/U4-NC-Pad8)` nets in `controller.net`).

Firmware confirmation (`firmware/src/bin/main.rs`): `NUM_THERMOCOUPLES = 3` (from `constants.rs`); SPI2 configured at 60 MHz, mode 0, with `sck` on GPIO5 and `miso` on GPIO10; three independent CS `Output` pins on GPIO4/GPIO6/GPIO7, toggled low/high around each `spi_bus.read()` to select one chip at a time (bit-banged CS, shared bus, sequential polling — not simultaneous reads). Each 4-byte read is parsed by `firmware/src/max31855.rs::interpret_max31855_read`, and a fault from that parse sets both a web-exposed fault flag and (if the zone is enabled in the active run config) trips `RunFailureReason::ThermocoupleFault { zone }`, which the main loop uses to abort a run and turn the heater off.

## 5. Known Limitations

Sourced directly from code comments and commit history — nothing below is fabricated:

- **Panic handler does not de-energize the heater.** `firmware/src/bin/main.rs`: `panic_handler` contains the comment `// TODO: what happens to the GPIO pins here?` immediately before an infinite `loop {}`. This means a firmware panic's effect on the heater-driving GPIO1 output (and therefore the physical heater) is an open, unresolved question in the code itself — not asserted to be safe.
- **Config retrieval workaround / unclear state handling.** In the `Running` state match arm: `// TODO: why can't I just get the config?` — the author flags their own state-management code as not fully understood/clean.
- **LED state mapping is a stand-in, not a final design.** `// TODO: use a lookup table to set color based on state` — the current per-state LED color assignment (`WHITE`/`GREEN`/`PURPLE`/`RED`/`OFF`) is explicitly marked as a placeholder implementation.
- **Heater-switch fault pin is not monitored by firmware.** The TPS1H200AQDGNRQ1's `~{FAULT}` output is wired only to test point `TP6` in the netlist; no GPIO net connects it back to the ESP32, and no reference to a fault-reading GPIO for the heater switch appears in `main.rs`. Hardware over-current/thermal-fault reporting exists on the board but is not used by the control loop — this is a gap between what the hardware supports and what the firmware currently reads, visible directly from comparing the netlist to the firmware.
- **Component-vs-library mismatch for two of the four protection/power ICs named in this document's brief.** `LM73100RPWR` and `MPM3606AGQV-P` remain as vendored KiCad library files (symbols/footprints/STEP models) under `hardware/controller/components/` even though neither appears in the current netlist, schematic, or PCB — they were superseded by `TPS2121RUXR` and `AP63203WU` respectively (see commits `d69e70c`, `fdfb582`). This is not a firmware/code TODO, but it is a real, observable inconsistency in repo state (dead library assets left behind after a hardware revision) worth flagging for anyone reading the component libraries at face value.
- **Diode-vs-TVS naming mismatch on the 12 V rail.** Commit `542887a` is titled *"Add TVS diode to 12V rail,"* but the part it actually adds (`D7`) is schematic symbol `Device:D` (a generic diode), not `Device:D_TVS` (which the design does use elsewhere, for `D5`/`D6` on the fan-tach lines). Whether `D7`'s physical BOM part is actually a TVS diode in a generic diode's clothing, or the commit message is simply imprecise, cannot be determined from the files in this repo.

## How to review

Work through the design systematically before answering:

1. **Power and ground.** For each supply rail and for `GND`, check which pins sit on it. Look for signal, enable, reset, data or sense pins tied directly to `GND` or to a supply rail where the spec or the part's function says they should not be. Look for two different rails joined together.
2. **Connectivity.** For each important interface the spec describes (buses, enables, resets, feedback networks, sensing paths, connectors), check that the expected pins share a net, and that no net merges signals that should be separate, such as two unrelated buses or a data line joined to a power or control line.
3. **Component identity.** For every two-terminal passive, check that its reference prefix (`R`, `C`, `L`), library part, description, footprint and value all agree with each other and with its role in the circuit. Examples: a pull-up or current-limit position occupied by a capacitor, or a decoupling position occupied by a resistor.
4. **Values.** Check each passive's value against the spec where the spec states it, and otherwise against its role. Examples: a pull-up three orders of magnitude off, a decoupling capacitor in millifarads in a small chip footprint, or a feedback or timing part inconsistent with the stated output or timing.
5. **Tolerances and ratings.** Check stated tolerance, voltage rating and dielectric fields against the part's description and its role (precision divider, current sense, reference, timing).
6. **Anything else.** Polarity, missing or extra components, open connections, footprint mismatches.

Rules:
- Base every finding on specific evidence quoted from the files: references, pin numbers, net names and values. Where the finding contradicts the spec, quote the relevant spec text too.
- Report only real deviations. Do not report pre-existing properties the spec documents, style issues, automatically generated net names, component ordering, or parts the SPICE deck leaves out by design.
- If you find several candidate issues, rank them by confidence, most likely first, and report at most 3.
